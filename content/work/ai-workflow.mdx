## 문제

API 연동, 테스트, 변경 영향 확인, 배포로 이어지는 개발 과정이 팀 안에서 각자의 프롬프트와 수작업 판단에 맡겨져 있었습니다. 같은 종류의 작업이라도 사람마다 결과물의 형태가 달랐고, 리뷰 기준도 매번 새로 정해야 했습니다. 재현 가능한 절차가 없는 채로는 팀 규모가 커질수록 이 격차가 더 벌어질 문제였습니다.

## 행동

밀리 바이브는 비개발자가 Claude Code 플러그인만 설치하면 밀리 디자인 시스템(MDS)과 책 데이터가 입혀진 미니앱을 만들 수 있는 사내 바이브코딩 플랫폼입니다. 이 플랫폼의 빌드·업로드·호스팅으로 이어지는 배포 파이프라인 전체를 설계하고 구축했고, 플러그인 스킬과 디자인 토큰 강제·외부 데이터 차단 같은 가드레일 일부를 개발했습니다. 비개발자가 쓰는 도구이기 때문에 코드 리뷰 없이도 산출물이 디자인 시스템을 벗어나거나 허용되지 않은 데이터를 끌어오지 못하도록, 가드레일을 배포 파이프라인 안에 넣어야 했습니다.

팀 AI 워크플로우 표준화는 동료와 함께 진행했습니다. Swagger 명세에서 API 코드 5개 파일을 자동 생성하는 스킬, QA 전에 AI 코드 품질을 자동 검토하는 절차, CLAUDE.md 기반 컨텍스트 표준화와 페르소나 시스템, Figma MCP를 통한 마크업 생성, AI 주도 TDD, PR 단계 AI 리뷰 체크리스트를 하나씩 만들어 팀 표준으로 정착시켰습니다. 개인별로 흩어져 있던 노하우는 주간 AI 워크샵에서 공유하고 다듬어 표준 절차로 남겼습니다.

가장 까다로웠던 부분은 변경 영향 분석이었습니다. 호출부 697곳을 사람이 하나씩 추적하는 일은 현실적으로 불가능합니다. 이를 멀티 에이전트 파이프라인으로 체계화해, 사람이 손대지 못했던 규모의 영향범위 전수 분석을 반복 가능한 절차로 만들었습니다.

## 성과

측정되지 않은 생산성 수치를 성과로 내세우지 않습니다. 대신 팀이 실제로 반복해서 쓰는 표준 산출물로 성과를 남깁니다.

- 밀리 바이브 배포 파이프라인을 통해 비개발자도 가드레일 안에서 미니앱을 만들고 배포할 수 있게 됐습니다.
- Swagger 기반 코드 생성, AI 코드 품질 검토, PR 리뷰 체크리스트가 개인 프롬프트가 아닌 팀 표준 절차로 자리 잡았습니다.
- 697곳 호출부 추적처럼 수작업으로 불가능했던 영향범위 분석이 에이전트 파이프라인으로 반복 가능해졌습니다.

AI를 도구로 잘 쓰는 것과 그 결과를 팀이 반복해서 쓸 수 있게 만드는 것은 다른 문제였습니다. 표준으로 남기지 않으면 다음 사람은 같은 시행착오를 그대로 반복합니다.
